## Context

参见 [proposal.md](./proposal.md) 的动机。FastAPI 后端已有创建单份内联 Markdown 评审、读取单个评审、读取 findings、提交 finding 决策、最终审批和读取报告的端点，但缺少任务列表、来源显示名称和决策读取投影。默认运行时为进程内实现，同时已有 SQLAlchemy 表结构供持久化适配器使用。

根目录 `openspec/specs/` 是公共契约的唯一来源。对应的前端组件 change 位于 `frontend/openspec/changes/add-directory-ai-review-workbench/`，只定义 UI 行为并引用本 change 的公共契约。

## Goals / Non-Goals

**Goals:**

- 以少量向后兼容字段和一个列表端点补足客户端刷新恢复能力。
- 让每个 finding 的最新人工决策可查询、可审计且严格幂等。
- 在服务端强制逐点审核完成后才能最终批准文档。
- 让进程内运行时和数据库适配器遵循相同应用服务接口。

**Non-Goals:**

- 不定义目录选择、路由、页面布局或前端状态管理。
- 不引入服务端批次或目录领域对象。
- 不改变 AI 的评审维度、模型策略或知识库索引流程。

## Decisions

### 1. 通过向后兼容查询扩展恢复状态

`ReviewCreate` 增加可选、长度受限的 `source_name`。新增 `GET /api/v1/reviews`，项目身份只取自认证上下文，不接受可覆盖项目范围的过滤参数。列表返回稳定倒序的轻量摘要；单个评审响应同步返回来源名称和计数。

findings 端点继续返回数组，只在元素上增加可空的 `decision`。`decision` 取创建时间最新的记录；相同时间以决策 ID 稳定裁决。这样保持现有 URL 和响应外层形状兼容。

### 2. 服务端执行逐点完成门槛和严格幂等

后端处理 `approve` 时验证每个当前 finding 的最新决定必须是 `accept` 或 `reject`。`re-review` 保持未完成；没有 finding 的成功评审仍允许最终确认。

finding 决策的幂等范围包含项目、评审、finding 和幂等键。后端将重试请求的 action/comment 与已存决策比较：同键同内容返回原结果，同键异内容返回 `409` 稳定错误。

### 3. 数据模型与运行时保持同一接口

应用服务协议增加列出评审的方法，并扩展现有返回投影。进程内运行时和数据库仓储共享相同行为测试。

数据库为 `review_runs` 增加可空 `source_name`；为 finding 决策查询增加支持最新记录的复合索引。已有 `created_at` 作为 `decided_at`。历史来源名称保持空值。

## Risks / Trade-offs

- **[创建请求超时后客户端可能重复创建评审]** → 本次不修改创建端点的幂等协议；列表提供来源名称和时间，后续可独立增加创建幂等能力。
- **[最新决策查询增加数据库成本]** → 为 finding 与创建时间增加复合索引，并在列表查询中聚合计数，避免逐条查询。
- **[历史决策的意见格式可能不一致]** → 幂等比较使用 API 校验后的 action 和原始 comment，不重写历史审计事实。
- **[默认进程内运行时重启会丢数据]** → 保留开发适配器定位；生产刷新恢复能力依赖数据库适配器。

## Migration Plan

1. 部署可空 `source_name` 和查询索引迁移；历史数据无需回填。
2. 部署后端兼容扩展和最终确认门槛，运行根 OpenSpec、API、持久化与集成验证。
3. 前端组件可在后端扩展部署后独立发布；旧客户端继续使用原请求形状。
4. 回滚后端代码时保留新增可空列和索引，避免破坏已写入数据。
