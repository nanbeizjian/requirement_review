## Context

参见 [proposal.md](./proposal.md) 的动机。当前 `frontend/` 业务工程已被删除以等待重写，因此本 change 将建立聚焦目录评审流程的新应用。共享 API 依赖根 change `openspec/changes/add-directory-ai-review-workbench/`，前端不拥有或复制这些契约。

## Goals / Non-Goals

**Goals:**

- 建立从目录选择到逐条 finding 审核和最终报告的完整浏览器流程。
- 让每份文档的处理相互隔离，并能从服务端恢复持久状态。
- 集中管理 API、身份、轮询和错误转换，使组件保持单一职责。
- 提供键盘可操作、角色感知且不依赖颜色表达状态的界面。

**Non-Goals:**

- 不在浏览器中持久化需求正文、身份凭据或审核事实。
- 不引入服务端批次对象、实时推送或专用前端状态库。
- 不恢复与本流程无关的旧知识库及项目管理页面。

## Decisions

### 1. 浏览器编排一份文件对应一个评审

目录选择器返回文件集合后，前端过滤 Markdown、读取 UTF-8 文本并逐份调用根契约中的评审创建端点。提交队列使用固定小并发，单项维护选择、读取、提交、评审、等待审核、完成和失败状态。失败重试创建新 review，避免复用状态未知的创建请求。

后端已将单文档 review 作为证据和报告边界；浏览器编排无需引入批次 API。相对路径只在当前选择预览中显示，服务端只接收清理后的文件名。

### 2. 使用聚焦工作台的 React 路由结构

使用 React、TypeScript strict、Vite、React Router、Vitest 和 Testing Library。主要路由为：

- `/reviews`：项目评审列表与目录导入；
- `/reviews/:reviewId`：文档状态、finding 记录、筛选、决策和最终确认；
- `/reviews/:reviewId/report`：最终 Markdown 报告。

目录导入、文件队列、状态摘要、finding 卡片和决策表单拆成独立组件。页面级 hooks 负责远端状态；当前规模使用 React 状态与 effect，减少额外依赖。

### 3. 单一 typed API client 和会话来源

所有网络访问集中在 typed API client，类型镜像已批准的根公共契约。SessionContext 是用户、项目和角色的唯一来源，每次请求注入身份头。viewer 只能读取；reviewer/admin 才呈现决策和最终确认控件，后端仍执行最终授权。

每次人工操作生成独立幂等键；网络重试复用该键，用户发起新操作时生成新键。错误适配器只向组件提供安全消息、错误码和关联 ID。

### 4. 可取消的有界轮询

创建成功后以 1 秒开始查询状态，逐步退避到最多 5 秒。到达等待人工审核、完成或失败终态时停止；页面卸载或 review ID 改变时通过 AbortController 取消。轮询失败保留最后成功状态并提供手动重试，避免无限快速请求。

### 5. 服务端状态驱动审核完成度

任务列表和详情每次加载都读取服务端的 summary、findings 和最新 decision。前端不使用 localStorage 作为审核事实。只有待决数量为零且无 `re-review` 时才启用最终确认；提交后仍以服务端响应为准。

## Risks / Trade-offs

- **[大量文件产生模型压力]** → 限制并发提交并清晰显示队列，不让单项失败中断其他项。
- **[目录选择的浏览器支持不同]** → 使用目录 input 渐进增强并提供多文件选择回退。
- **[创建超时可能形成重复任务]** → 重试前提示会创建新评审，并通过来源名称和创建时间帮助识别。
- **[默认内存后端重启会丢状态]** → UI 始终以 API 为准；生产恢复依赖根 change 的持久化实现。

## Migration Plan

1. 先应用并部署根公共契约 change。
2. 发布前端静态资源并执行组件 OpenSpec、lint、typecheck、测试和构建验证。
3. 回滚前端只需恢复上一版静态资源，不影响已创建评审或人工决策。
